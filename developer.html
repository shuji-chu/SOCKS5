API

API 接入说明

当前前端使用的基础地址默认为 https://web.lynli.me/api/v1，可在加载前通过 window.SOSKS5_API_BASE 覆盖。请求 JSON 时使用 Accept: application/json、Content-Type: application/json；需要登录的接口使用 Authorization: Bearer YOUR_TOKEN。

GET  /user/info
GET  /user/plan/fetch
GET  /user/getSubscribe
GET  /user/invite/fetch
GET  /user/invite/customers
GET  /user/bot/status
GET  /user/notices
POST /user/order/save
POST /user/order/checkout

以上是现有前端调用代码中能确认的路径，并不保证上游每个环境都已启用。订单创建与结算接口不等于订单历史接口；当前订单历史页面会尝试常见列表路由，但仍需后端明确提供“只返回当前登录用户订单”的接口，才能保证完整性。禁止在客户端通过用户传入的 user_id 查询他人订单。

订单金额单位：现有客户端将常规金额字段按“分”转换为人民币元展示。若服务端字段单位不同，应由 API 契约明确声明，不能依赖猜测。

OBJECT STORAGE

OSS / Cloudflare 图片链路

管理面板通过后端上传接口提交图片；后端校验文件类型、大小和真实图片格式，重新编码成 WebP 后上传 S3 兼容对象存储。浏览器只拿到公开图片 URL，不接触 AccessKey Secret。

必需的服务端环境变量（只配置在容器 / 部署平台，不要提交到 Git）：
S3_ENDPOINT_URL=https://你的对象存储S3兼容端点
S3_REGION=你的区域
S3_BUCKET=你的Bucket名称
S3_ACCESS_KEY_ID=服务端专用AccessKeyId
S3_SECRET_ACCESS_KEY=服务端专用AccessKeySecret
MEDIA_PUBLIC_BASE_URL=https://img.你的域名
USER_API_BASE=https://web.lynli.me/api/v1
CORS_ORIGINS=https://shuji-chu.github.io
ADMIN_AUTH_VERIFY_URL=https://你的认证服务/一个需要管理员权限的验证接口
HOME_BANNERS_OBJECT_KEY=site-config/home-banners.json

接口：POST /api/v1/admin/media/upload 上传图片；GET/PUT /api/v1/admin/home-banners 管理轮播配置；GET /api/v1/public/home-banners 提供首页公开读取。管理员接口必须通过服务端身份验证。

  1. 在 OSS 创建专用 Bucket 与最小权限 AccessKey，只允许指定 Bucket 的对象读写。
  2. 把图片访问域名绑定到 OSS / R2 的自定义域名，并在 Cloudflare 配置 DNS、HTTPS 和缓存策略。
  3. 若使用 Cloudflare 代理，确认对象存储自定义域名的回源方式支持该 Bucket；不要把管理 API 或私有对象直接设为公开。
  4. 为公开图片路径设置较长缓存；配置 JSON 使用 no-store，确保广告更新后能及时生效。
  5. 将 API 路径反代到运行此仓库后端的服务，并设置 ADMIN_AUTH_VERIFY_URL 为真实、需要管理员权限的验证接口。未配置时管理接口会 fail closed。

此仓库无法替你设置云厂商控制台、DNS、Cloudflare 代理开关或部署环境变量。代码已提供接口实现，但只有部署并正确配置这些变量后，云端上传和跨设备发布才会生效。

SECURITY

安全与防爬清单

  • 前端不是安全边界：HTML/JS、商品目录、接口地址都可被查看。真正的权限、库存、价格、订单归属必须在后端校验。
  • Cloudflare：启用 WAF Managed Rules、Bot Fight Mode（按业务兼容性测试）、针对登录/注册/验证码/下单/上传设置 Rate Limiting；不要对支付回调或 API 盲目挑战。
  • 源站：只允许 Cloudflare 回源 IP 访问 Web 端口，管理端口不公开；强制 HTTPS，关闭目录列表与调试模式，限制 CORS 到明确站点。
  • 认证：管理员 API 每次请求验证角色和 Token；用户订单 API 从 Token 解析 user_id，绝不相信客户端提交的 user_id/order owner。
  • 浏览器 Token：当前前端兼容旧版 localStorage Token，若页面发生 XSS，Token 可能被窃取。避免不可信脚本和第三方组件，配置严格 CSP；长期应迁移到服务端 HttpOnly、Secure、SameSite Cookie 会话。
  • 上传：限制大小与像素，按文件内容解码后重编码，生成随机文件名；禁止 SVG/HTML/脚本上传；不把 OSS 密钥写入前端。
  • 反爬：公开页面可被抓取，不能承诺绝对防爬。用 WAF、速率限制、缓存、分页、异常流量告警和最小化公开字段降低滥用。
  • 隐私：不要通过第三方二维码网站处理订阅链接、卡密或订单凭证；只在订单所属用户已认证且符合支付/发货状态时返回敏感交付数据。
  • 密钥：不要在 Git、截图、日志或客服消息中暴露 API Key、支付密钥、OSS AccessKey 或订阅链接；发现泄露应立即轮换。
ORDERS

订单明细字段建议

完整订单接口应至少返回订单号、商品 ID / 名称、规格或周期、数量、币种、基础金额、增值服务金额、折扣、实付金额、支付方式、订单状态、创建时间、支付时间、发货时间和更新时间（统一 ISO 8601 时间戳，前端按秒展示）。详情 API 必须校验订单归属，并且未支付订单不得返回卡密或订阅链接。

当前静态站无法独立确认上游是否启用了订单列表路由或保存了所有字段。面板代理会尝试 /user/order/fetch、/user/order/list、/user/orders；必须确认上游根据 Bearer Token 只返回当前用户的数据。若上游没有这些接口，仍需在真实业务后端实现订单列表和详情 API 才能完成端到端验收。
